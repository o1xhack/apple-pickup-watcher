# 本地库存历史

桌面后台把库存历史写入设置目录旁的 `inventory-history.sqlite3`。macOS 默认路径：

`~/Library/Application Support/apple-pickup-watcher/inventory-history.sqlite3`

不需要启动额外服务。窗口隐藏时继续记录；退出期间不查询，下一次启动会建立新会话并继续累积。
现有数据库不自动清空或裁剪；这个版本之前未保存的日志无法补回。网页暂不增加历史 tab 或分析界面。

## 保存什么

- `sessions`：应用启动和正常退出时间；没有退出时间表示没有确认正常收尾，不能当作一直在运行。
- `cycles`：每轮结束时间、目标数、是否健康、下一轮预计等待秒数和是否限速。
- `targets`：地区、门店、SKU、机型名称，目标删除后历史仍保留。
- `observations`：每轮各目标的实际检查时间、有货/无货/未知、未知原因、连续失败次数。
  未开放取货的 Apple 原文也保留；原始网络错误不保存，避免误记私有代理信息。
- `events`：开始、暂停、故障提示。库存结果以可靠投递的整轮快照为准，不依赖可能丢弃的界面变化事件。
- `notifications`：真实到货提醒的生成时间、机型/颜色/门店文案、公开 Apple 商品链接、重要警告设置、是否配置远程推送和发送处理结果。
  测试提醒不混入真实到货历史。发送成功表示应用的发送调用成功，不保证手机已收到或已响铃；
  `queued` 表示尚无完成结果，退出/异常中断后不能据此认定已发送或失败。

所有时间都是 Unix 毫秒（UTC 时间轴）。做按天/小时分析时，再转换为 `America/Los_Angeles`，正确处理夏令时。

## 以后怎么分析

指定机型、容量、颜色、门店和时间范围后，可以直接只读查询 SQLite，无需先做网页 tab。
应当区分：

1. 同一次连续监控中，先明确无货、后明确有货：补货候选，实际变化发生在两次检查之间。
2. 启动或恢复监控后第一轮就是有货：首次发现，不证明刚补货。
3. 中间有未知、限流、暂停、进程退出、漏记或明显超过预期的采样间隔：只能报告恢复后发现有货，不能计算精确上架时间。
4. 持续有货的重复轮询：只算一次连续有货区间，不按每轮累加成补货次数。
5. 不同门店、SKU 的样本分开统计；小样本不能推断未来固定补货时间。

只读汇总脚本（JSON 输出，无需安装依赖或重启应用）：

```sh
python3 scripts/analyze_inventory_history.py "$HOME/Library/Application Support/apple-pickup-watcher/inventory-history.sqlite3"
```

结果按洛杉矶当地日期、小时、门店及 SKU 分组，列出首次发现、无货后有货的候选区间、
恢复查询后发现有货及采样覆盖。跨午夜仍然有货只记为持续有货；通知条数不参与补货统计。
未知、暂停、跨会话、缺失目标采样或超过上一轮预计等待两倍的空档，均不能认定为精确补货。
小时统计是采样次数，不代表持续时长或未来补货概率。当前历史仅保留未开放取货时的原文，
普通无货时的所有官网提示文案未保存，因此不能事后声称观测到了“明天晚点再看”这句话。

## 数据可靠性与读取

SQLite 使用 WAL、`synchronous=FULL` 与事务；一轮快照要么完整写入，要么回滚。
已提交的数据可跨重启保留。正常退出尽量排空写入队列；强制杀进程/断电可能缺少尚未提交的末尾记录，
不能承诺每个尚在内存里的事件都已保存。

写入由独立线程完成，不能让数据库慢或写入失败阻塞库存查询和通知。写入失败/队列已满会提示历史可能不完整，
现有数据库不会被悄悄替换。不能把数据库故障改写成无货。

`GET /api/state` 中的 `history` 提供文件路径、会话号、最近写入时间及本次运行中最近的记录错误；
为 `null` 表示本次历史存储未启用，应检查启动提示。该接口不返回 Bark 密钥或代理配置。

应用运行时，`-wal` / `-shm` 是正常配套文件。不要只复制主数据库来当作一致备份；
分析副本用 SQLite backup API，或正常退出后再复制。读取生产数据库应使用只读连接，不执行清理或更新。


## 请求与恢复调度（schema v2）

`network_events` 单独记录实际出站开始（`request_started`）、完成（`request`，含 HTTP 状态和耗时）、`cooldown_started`（含截止时间）、`probe_started`、`probe_recovered` 及 `recovery_step`。本地冷却等待不会制造 HTTP 541 请求记录；取消或进程退出可能留下只有开始、没有完成的请求，不能当作 Apple 拦截。`request` 的 occurred_at_ms 是发送时间，完成时间可用 duration_ms 推算。

只保存白名单字段：地区、匿名线路标签、请求类别、SKU 数、HTTP 状态、分类、耗时和调度时间；不保存 URL、Cookie、代理地址或原始网络错误。schema v1 自动迁移，旧库存历史保留，旧记录没有新增网络明细，不能回填猜测。

冷却采用客户端现有的 5/10/20/30 分钟阶梯；全部线路冷却时，引擎按最早截止时间探测，不再叠加整轮失败指数退避。预算仍有约束。探测只发取货请求，不额外暖场；失败继续冷却。首次真实拦截后间隔下限 300 秒，一小时内再被拦提高到 600 秒；每连续 6 次取货请求成功降一档，直至回到用户基础间隔（本机 180 秒）。本地等待不影响恢复档位。恢复策略仅存内存，重启后重新观察；不会改写设置间隔。默认连续有货去重；开启全局重复提醒后按每次新的有效有货采样提醒。

## 当前提醒流程

仅保留库存监控和到货通知，不再触发 Codex 购物袋操作。通知分组为 `Apple 库存监控`，目标可单独勾选 Critical Alerts；重要提醒使用 `anticipate` 铃声，到货正文和购物链接以 JSON POST 发送。默认连续有货不重复通知。全局「有货重复提醒（全部监控）」开启后，所有现有及新增目标每轮新的有效有货采样均发送提醒；未知、冷却和旧快照不发送。开关重启后保留，单个目标的重要警告、通知链接和铃声设置不变。

## 本地定制版更新

此定制版关闭上游更新检查、提示和安装入口，不请求上游 Release，也不注册 updater 插件或权限。后续通过本地构建更新，避免上游安装包覆盖美国监控及通知改动；更新时保留现有 settings 与库存历史。

## 网页统计与分享

网页新增「统计与历史」页，可按本次开始、今天、全部历史或自定义日期筛选，默认仅包含当前监控目标，可勾选已删除目标。所有日期按 `America/Los_Angeles`（含夏令时）解释。顶端总览显示本次开始以来的统计，每分钟更新。

`GET /api/statistics` 为只读接口，接受 `fromMs`、`toMs`、`allTargets`、`offset`；默认从当前会话最后一次 started 事件统计。数据库使用只读连接和一致事务，查询在独立阻塞任务中运行，不触发 Apple 请求、不更改监控或通知配置。分页固定每页 100，最多前 10,100 条，可用日期缩小范围；翻页冻结时间边界。

检查按目标（门店×SKU）与实际 checked_at_ms 去重，重复保存同一快照不重复计数；扫描轮次计有实际采样的去重轮次。台数不可从这些数据推算。机型／容量／颜色按 SKU 展示，包含门店列表及逐条采样历史。HTTP 请求数统计应用全部目标，不能归属为每个 SKU 各一次请求。

有货检查次数包含持续有货的多次实际采样；有货区间另计。只有同会话内相邻明确无货→有货、无启停事件、间隔不超过上一轮预计等待两倍时才记补货候选。范围首条有货、未知恢复、重启、启停或明显缺口后的有货均为首次／恢复后发现，不当作明确补货。统计不是手机实物数量或未来放货预测。

网页支持中文／English，本浏览器保存语言偏好。分享仅生成所选范围的机型、门店及聚合统计文本，通过系统分享面板或复制分享；不公开页面，不包含 Bark 地址、代理、凭证，也不修改现有 Tailscale 设置。

## 状态页版式

状态页默认全部历史（当前目标），筛选器折叠在报告外。报告上方展示机型、日期范围、当前库存状态；主要卡片为扫描轮次、检查次数、有货记录、门店数、配置数和请求错误。请求错误计所选时间内已记录的 HTTP 状态码 ≥400，不把目标采样失败次数当成 HTTP 请求次数。口径说明仅放底部。截图模式只显示报告卡，返回按钮可退出；监控配置与通知不变。
